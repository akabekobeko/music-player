# MusicBrainz API / Rate Limiting (私訳)

## はじめに

MusicBrainz のリソースは有限であり、MusicBrainz データベースをできるだけ多くのインターネット コミュニティーに提供したいと考えています。しかし、1 日のうち特定の時間帯には [MusicBrainz API](musicbrainz-api.md) へのリクエスト数が処理能力を超えます。これらのリクエストをすべて受け入れるとサーバーが過負荷になり、全員に対してサービスが劣化してしまいます。このため、Web サービスにはレート制限を設けており、クライアントが一定期間内に発行できるリクエスト数を制限しています。

## スロットリングの仕組み

サイト全体の健全性を守るため、ブロック / スロットリングのルールはいつでも変更することがあります。2012-01-08 時点のルールは次のとおりです。

リクエストがサーバーに届くと、次の順序で 3 つの条件を確認します。

- User-Agent 文字列: このアプリケーションからのリクエストが多すぎないか?
- 送信元 IP アドレス: この特定の IP アドレスからのリクエストが多すぎないか?
- 全体: MusicBrainz サーバー全体がこのリクエストを処理できないほど混み合っていないか?

これらのいずれかの答えが「はい」なら、リクエストは 503 Service Unavailable エラーで拒否され、処理は停止します。そうでなければ次の確認へ進みます。すべての確認を通過すれば、リクエストは受け入れられます。各確認の詳細は以下を読んでください。

### User-Agent

[headphones](https://github.com/rembo10/headphones/wiki) に関連する user-agent について: (平均して) 1 秒あたり 50 リクエストを通し、残りを拒否 (http 503) します。これには複数バージョンにわたる headphones 自身と、headphones から呼ばれたと判断できる場合の beets (headphones が使うタガー) が含まれます。

"python-musicbrainz/0.7.3" について: (平均して) 1 秒あたり 50 リクエストを通し、残りを拒否します (ただし最近はこれに達していません)。

「匿名」の user-agent (後述) について: (平均して) 1 秒あたり 50 リクエストを通し、残りを拒否 (http 503) します。

その他の user-agent について: 通します。

### 送信元 IP アドレス

MusicBrainz と別途合意していない限り、ルールは次のとおりです。

あなたの IP アドレスがリクエストを発行する速度が計測されます。その速度が高すぎる場合、速度が再び下がるまで、あなたのすべてのリクエストが拒否 (http 503) されます。現在その速度は (平均して) 1 秒あたり 1 リクエストです。

たとえば、あなたのリクエストが 1 秒あたり 4 リクエストで届いている場合、25% を受け入れて残り 75% を拒否するのではなく、速度が 1 秒あたり 1 以下に下がるまで 100% を拒否します。

### 全体

(平均して) 毎秒 300 リクエストを通し、残りを拒否 (http 503) します。

## User-Agent スロットリングの詳細

行儀の悪いアプリケーションは MusicBrainz サービスの品質を劣化させることがあります。そのようなアプリケーションは (User-Agent ヘッダーに基づいて) そのアプリケーション固有のスロットリングの対象になることがあります。

行儀の悪いアプリケーションを見つけた場合、私たちはその保守者に連絡を取って問題に対処したいと考えています。したがって、User-Agent 文字列には保守者に連絡できるだけの十分な情報が必要です。このルールを破る User-Agent を、私たちは「匿名」と呼びます。

匿名の User-Agent、すなわち前述のスロットリングの対象となるものは次のとおりです。

| User-Agent 文字列 | バージョン |
| --- | --- |
| <空欄> | - |
| Java | すべて |
| Python-urllib | すべて |
| Jakarta Commons-HttpClient | すべて |
| Apache-HttpClient | UNAVAILABLE (java 1.4) |

## 良き市民として Web サービスを賢く使うには?

(「ブロックされないようにするには?」/「ブロックされました! 解除するには?」)

MusicBrainz にブロックやスロットリングをされないよう、アプリケーションは以下の助言に従ってください。他の人が保守するアプリケーションを使っている場合は、問題を直してもらうためにその保守者に連絡する必要があるかもしれません。

あなたがアプリケーションの作者で、アプリケーションがブロックやスロットリングをされ、このページの情報のいずれも問題解決に役立たなかった場合は、[お問い合わせ](https://musicbrainz.org/doc/ContactUs)いただき、問題について相談してください。

### 意味のある User-Agent 文字列を提供する

MusicBrainz に送るすべてのリクエストには User-Agent ヘッダーを含める必要があり、その User-Agent には私たち (MusicBrainz) がアプリケーションの保守者に連絡できるだけの十分な情報が必要です。User-Agent 文字列にはアプリケーションのバージョン番号も含めることを強く推奨します。これは問題があったときに連絡できるようにするためです。User-Agent 文字列は次のような形を推奨します。

```
Application name/<version> ( contact-url )
```

または

```
Application name/<version> ( contact-email )
```

2 つの例:

```
MyAwesomeTagger/1.2.0 ( http://myawesometagger.example.com )
MyAwesomeTagger/1.2.0 ( me@example.com )
```

私たちのクライアント ライブラリーは現在、User-Agent 文字列を設定する関数をサポートしています。[私たちのライブラリー](https://musicbrainz.org/doc/Developer_Resources)のいずれかを使っている場合は、ライブラリー経由で User-Agent 文字列を設定する呼び出しを加える必要があり、それでアプリケーションは再び動作するはずです。

### スケジューリング

アプリケーションが 1 日の特定の時刻に起動して何らかの処理を行うようにするのは控えてください。たとえば、アプリケーションが現地時間 03:00 に起動して MusicBrainz に大量のデータを問い合わせるのは悪い考えです。このアプリケーションが世界中の多くのユーザーに配布されると (たとえば Linux ディストリビューションで)、1 日のさまざまな時刻に、しかし常に毎正時の始まりに、MusicBrainz はそのアプリケーションからのリクエストで過負荷になります。また、あなたのタイムゾーンの 03:00 は、世界のどこかでは MusicBrainz のピーク時間かもしれません。このようにアプリケーションを作り、それが私たちのサービスに影響を与えた場合、そのアプリケーションをブロックします。

バックグラウンドで実行したいタスクがあり、オフピークの時間帯に行いたくなった場合は、アプリケーションが 1 日を通してランダムな間隔で呼び出しを行うようにしてください。アプリケーションが呼び出しを 1 日に分散させれば、MusicBrainz サーバーの負荷も 1 日に分散され、人為的なピーク時間を生まずに済みます。

### 変更の確認

メタデータが変わったかどうかを確認するために MusicBrainz をポーリングするアプリケーションにしたい場合、それはやめてください。メタデータは実のところそれほど頻繁には変わらないため、変更のポーリングは良い結果をほとんど生みません。現時点では、メタデータが変わったことをユーザーに知らせる良い仕組みはありませんが、将来対処したいと考えています。
